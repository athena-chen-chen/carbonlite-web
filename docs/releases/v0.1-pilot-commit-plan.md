# Pilot release commit plan

Recommendation: one frontend pilot-release commit and one backend pilot-release commit on the existing `release/v0.1-pilot` branches. These represent the already reviewed integrated candidate; splitting the hardening cycle now would create intermediate states that were not release-tested. No automatic staging, commits, tags, pushes, migrations, or deployment.

Suggested frontend commit message: `release: freeze v0.1 pilot frontend and deployment runbooks`

Suggested backend commit message: `release: freeze v0.1 pilot API hardening`

Suggested tag in each repository after review: `v0.1.0-pilot`. Record both resulting SHAs in the deployment record; do not amend a published release to fill a self-referential SHA.

Before committing: compare source against the saved reviewed manifests, inspect staged diff and untracked fixtures, verify no credentials/private backups/uploads are staged, and review the validation limitations. The targeted release checks do not claim the complete historical suite is green. Two existing authorization payload tests and a Data Records loading assertion were known failures in the freeze audit and are left unchanged.
