## Explicit Render storage verification

1. Read the persistent-disk configuration and record its absolute mount path. Do not infer durability from a writable directory.
2. In the actual runtime shell, inspect `pwd -P`, resolve `./uploads` with `realpath`, and inspect the filesystem mount covering that path. Record results without environment dumps.
3. Confirm the reviewed API process uses that working directory. Both upload writes and source reads resolve relative to it; stored file URLs are `/uploads/<id>`.
4. Mount the persistent disk at `<actual-api-working-directory>/uploads` if Render permits that path. The reviewed code does not consume a separate UPLOAD_DIR variable; setting one would not redirect storage.
5. Verify write permissions and exactly one API replica with no independent autoscaling replicas.
6. Upload a synthetic source through the app and record its document ID and SHA-256, without customer data.
7. Restart the service; retrieve the same source via authenticated download and compare its hash.
8. Redeploy the same reviewed release; retrieve the source again and compare its hash.
9. Confirm the platform's disk behavior during instance replacement; record any recovery procedure rather than assuming persistence.
10. Record total/free disk space, utilization, and the monitoring threshold.

Configuration can solve the relative `./uploads` path IF a supported persistent mount covers the resolved directory. This has not been verified. If the actual Render service cannot mount that path or run from a suitable working directory while loading the reviewed build, STOP: report the platform restriction and request the smallest configurable storage-root change. Do not redesign storage automatically.
