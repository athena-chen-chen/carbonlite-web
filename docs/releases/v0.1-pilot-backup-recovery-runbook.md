# v0.1 pilot paired backup and recovery runbook

Status: procedure prepared; no pilot backup or restore drill is claimed. No live data is changed by preparing this document.

## Preconditions and evidence record

Identify the exact Neon project/branch/endpoint/database/schema and Render service/disk first. Record both release SHAs, migration inventory, UTC recovery-point timestamp, operator and evidence location. Never record connection strings, signing keys, passwords, tokens or provider API keys. Use secret-managed/libpq service credentials and restrict access to backups, which contain customer data and authentication hashes.

## A. Database backup

1. Verify the actual Neon plan's backup/PITR capability, retention, earliest/latest recoverable times, and recovery destination behavior in the provider console. A general provider feature description is not evidence it is enabled for this branch.
2. Establish a pre-deployment recovery point. Pause pilot writes and drain extraction/confirmation activity to make the paired source capture consistent.
3. If taking a logical dump, use a protected connection profile with an authorized `pg_dump --format=custom --no-owner --no-acl` workflow. Save into restricted storage outside the application/public directories. Record DB identity, dump timestamp, size and SHA-256 without credentials. Inspect the dump catalog with `pg_restore --list`; this only checks readability and does not prove restoration.
4. Verify encryption/access restrictions and an independent durable copy. Record last successful backup and an actual restore-capable recovery point before unpausing writes.
5. Pilot operating recommendation: paired daily recovery points and a new pair before deployment/migration, at least 14 days retained unless the agreed policy requires longer. Record the accepted maximum data-loss window (daily backup can lose up to 24 hours). These are recommendations until configured and verified; inspect PITR coverage separately.

## B. Source-file backup

1. Resolve the persistent uploads directory from the actual backend working directory/mount; include every source object referenced by the recovery-point database, plus retained/orphaned sources needed by policy. Do not rely on a DB dump to include bytes.
2. While writes remain paused, archive that directory preserving paths and permissions. Record archive timestamp, size and SHA-256. Extract into a temporary verification directory and inspect representative files; never extract over live uploads.
3. Copy the archive and manifest to restricted durable storage independent of the Render instance/disk. A second directory on the same volume is not an independent backup.
4. Use the same daily/pre-deployment schedule and retention as the paired DB point. Record successful copies and retrieval tests. Do not silently delete source archives while matching DB recovery points remain retained.

## C. Paired recovery point

Record a pair ID linking DB dump/PITR timestamp, uploads archive, source-file checksum inventory, code SHA pair, migrations and verification results. Keep writes paused across both captures, or document and reconcile the consistency boundary explicitly. Resume only after successful capture and independent-copy verification. Do not call two unrelated timestamps a tested pair.

## D. Isolated recovery drill

1. Create a new isolated disposable database/branch and isolated API directory/instance. Confirm explicitly that neither destination is live pilot data. Never overwrite or restore into main/live pilot workspaces.
2. Restore the chosen dump or PITR point to that new destination. Verify migration checksums/schema compatibility before starting the app. Do not run reset, db push, speculative backfill, or rewrite applied migration history.
3. Restore the paired uploads archive into the isolated instance's resolved uploads directory; verify hashes and permissions. Supply separately controlled test secrets through the isolated environment; never commit recovered credentials.
4. Start the reviewed backend and frontend pair pointed only to the restored environment. Keep automated mail/external side effects disabled and use an authorized synthetic test identity.
5. Retrieve a representative uploaded synthetic source via the authenticated download endpoint and compare its bytes/hash.
6. Compare ActivityData IDs/counts, quantities/units/dates, source identifiers, snapshots, factor provenance and calculation/audit evidence with the recovery-point manifest. Verify report totals remain unchanged.
7. For the two-row release smoke fixture, verify Electricity 980 kWh Alberta = 519.40 kgCO2e and Water 18 m3 tracked with zero GHG; when testing a different paired fixture, use its recorded totals instead.
8. Check health/live and health/ready, and download the regenerated report/CSV/PDF. Record recovery time and any missing source/calculation evidence.
9. Record DB restore / source restore / combined recovery PASS or FAIL, reviewer, timestamps and retained evidence. A successful dump listing or startup alone is not a passed drill.
10. Leave the live service untouched. A real failover or destination switch requires a separately authorized operator decision.
